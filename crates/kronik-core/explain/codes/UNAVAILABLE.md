The daemon cannot serve the request right now: it is starting or shutting down, it stopped accepting turns after a fatal error such as a failed log write, or the data directory's file system is below `[log] disk_reserve`, where new inputs and changes are refused until there is room. This code exists so that clients can tell a temporary state of the daemon from an error in their request.

To fix it, retry shortly. If it persists, read the message and the daemon log. Below the reserve, free disk space (old snapshots, foreign actors' data; `kronik foreign remove` and rollback still work) or lower the reserve. After a fatal error, fix the cause, for example a full disk, and restart the daemon.

For `serve`, `restore`, `keys wrap` or first key creation during `serve --init`, this also means another daemon or offline operation owns the data-directory lock. Stop that owning process, or use a different `--data-dir`. A missing or stale API socket is not evidence that the directory is free. Do not remove key files or bypass the ownership check.

From a replay (a proposal, `kronik replay`, a preview, a message into a fork) or `kronik upgrade check`, with the message `replay could not run: maximum concurrent limit of N for ... reached`, it means the Wasm instance pool had no room for a replayed turn: a replayed `call` keeps its caller's instance while the callee runs, so a chain of calls holds one per link, and a daemon's replays share its pool with its turns. Nothing was compared, and the check writes no report: it is not a behavior difference. The daemon clamps a replay's requested workers to the room its pool has for those workers and their calls, so asking for more workers than fit no longer causes this by itself. Run it again, with fewer `--threads` (`--workers` for the check) if it persists.

As the outcome of an actor's call turn (input source `CALL`) that a start wrote, it means the daemon stopped while the call waited for its callee, after its caller had timed out: the call never ran. Its caller had already failed or gone on without the answer. A compensation the call carried is not sent, and nothing is orphaned. If the change still matters, send it again.

As the outcome of an open turn's re-run, on three starts, it means the prerequisite the turn recorded did not become available during any start's retries. The host closed the turn as failed under its own execution id, with the effects it had recorded, instead of running it ahead of that actor's inputs at every start and keeping its begin's log segment from retention. The failed turn's message counts the starts. A message or timer input other than a call's is in dead letters; an HTTP input is recorded under its `Idempotency-Key`. Fix what the turn needs, then resend the dead letter (a new root input) or make the HTTP request with a new key. A recorded secret value that is still unavailable (`SECRET_UNAVAILABLE`) is not closed this way: the turn waits for it without bound, because the value is part of its record.
