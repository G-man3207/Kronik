# 0096. microVM snapshot ownership and fixed vsock protocols

- **Status:** Proposed. Implemented, never run on a host with KVM; awaits maintainer ratification.
- **Date:** 2026-11-07

## Control and readiness

Firecracker 1.17.0's HTTP server keeps connections alive. Kronik uses the installed Hyper HTTP/1 client with an 8 KiB header buffer, an 8 KiB response-body limit and an `Env` deadline; a bodyless 204 completes at the HTTP message boundary, not transport EOF. Boot is bounded separately. A failed pause response is uncertain: recovery still attempts resume and otherwise stops the owned VMM cgroup. It must not call `Process::kill` while the supervisor has a pending `Process::wait`, because the existing runner serializes those operations on its child mutex.

The data bridge uses Firecracker's hybrid UDS `CONNECT 10000\n` exchange, whose `OK <port>\n` reply is bounded and checked. That reply only establishes vsock. Guest PID1 first connects to the configured loopback TCP port, then sends the exact `KRONIK/1 READY\n` acknowledgement. The host waits for it before exposing the HTTP sender. Both sides use bounded buffers and deadlines; there is no health endpoint assumption or synthetic echo.

Failures after READY that could involve an HTTP send/read remain `Io`/outcome-unknown. The bridge does not safely reconnect and retry that request, including an unusable pooled sender. Pre-READY dial failure still proves no HTTP request was sent. Existing gVisor/trusted outcome handling is unchanged.

Graceful shutdown is architecture-independent. A second fixed guest vsock port, 10001, accepts only host CID2 and the bounded exact `STOP\n` frame. It acknowledges `OK\n` before signaling guest PID1's existing termination/reap/sync path (PID1 gives the guest's processes up to two seconds after `SIGTERM` and stops waiting as soon as none is left: the first stop on KVM waited the two seconds out every time and missed the second), which ends the VM with a restart: Firecracker has no guest power management, so a power-off would leave the VM halted and the VMM running, while a restart (`reboot=k` on x86_64, PSCI on aarch64) makes Firecracker exit. It is not a configurable RPC or command executor. The data and control listeners bind before application fork/threads; the control listener does not depend on spare data-connection capacity. `SendCtrlAltDel`, which Firecracker rejects on aarch64, is not assumed.

## Checkpoints and forks

The existing main-drain and per-actor call gates remain the M14 authority for the checkpoint LSN. A restart waits for a checkpoint of that actor instance to finish. New actor instances have separate runtime/cgroup/output identities, so delayed work cannot target an actor removed and re-added under the same name.

A full checkpoint pauses the VM, asks Firecracker for a full snapshot with `sync_snapshot_files=true`, synchronizes the writable data drive, and copies the data and immutable root into private staging. The snapshot's two files stay where the VMM wrote them, each bound into its jail (ADR 0095): the daemon copies them into the staging as new files private to its user (a reflink where the file system has them), refuses one that is not a regular file with one link or that is empty, and then empties them; the memory is on the disk twice until then, which the space check counts. Data copies are fully allocated independent files, not reflinks: subsequent production writes must not acquire unreserved COW extents. Immutable root and snapshot backing may use reflinks. The actual actor filesystem is checked against the disk reserve, including guest memory and the complete finite drive. Resume-or-stop recovery covers uncertain pause, API, copy and ENOSPC outcomes. Interrupted raw-memory outputs are emptied after recovery and swept after owned VMMs exit during startup/offline cleanup.

Publication syncs files and directories and uses no-replace rename. Metadata records its schema, the exact tool identity, host-kernel/CPU identity, immutable-root digest and resource projection. This is a conservative same-tools/same-host contract, not a tested cross-version or cross-machine compatibility promise. A mismatch fails with an explicit reason rather than attempting an unchecked restore.

A fork restores from real Firecracker memory/state, with its own fully allocated data drive and private immutable root/memory/state backing. These backing inodes belong to the copy's lifetime, not checkpoint retention. Preparation owns a new private directory before copying; every failure/cancellation removes only that new directory. Once a VMM is spawned, the existing actor/copy lifecycle owns cleanup before boot/restore protocol awaits. Fork stop kills/reaps the process before removing its private runtime and backing. Original production data is never replaced.

## Known limits of restored copies

Two things about a copy restored from a snapshot are as Firecracker documents them (v1.17.0, `docs/snapshotting/snapshot-support.md` and `random-for-clones.md`), and Kronik does nothing about either today. They are stated here so that a ratification is informed.

*Wall clock.* A microVM restored from a snapshot resumes with the guest's wall clock continuing from the moment the snapshot was taken, and Firecracker says the clock should be updated from the guest side; there is no guest time synchronisation in this design, and the restore request does not set `clock_realtime` (an x86_64 option that makes the guest clock jump forward, needing host Linux 5.16 or newer). A fork's guest therefore sees a wall clock that lags the host's by the age of its checkpoint.

*Unique values.* Firecracker's documentation calls a snapshot that is resumed more than once insecure: unique identifiers, random numbers and cryptographic tokens that are meant to be used once may be used twice, and the original microVM counts as insecure too once any copy runs. The VMGenID device, which Firecracker always enables and which Linux honours from 5.18, makes the guest kernel reseed its own random generator when a copy resumes. It does not change random state that a program keeps in user space inside the snapshotted memory (a user-space generator, a prepared nonce or session key), a stored random seed file, or `/proc/sys/kernel/random/boot_id`, which reads the same in every copy. Kronik resumes the original after a checkpoint and restores every fork from the same checkpoint, so every use of `fork_mode = sandbox` on a microVM actor is this case, and the code neither removes seed files, changes the boot id, nor asks programs to reseed. A foreign actor whose forks must not repeat a value that the original or a sibling produces would have to reseed itself on restore, and Kronik gives it no signal that a restore happened. This is for the maintainers to weigh before the level is offered.

## Verification contract

Real-socket regressions cover keep-alive 204, TCP-dependent READY, fragmented/rejected/timed-out STOP and outcome classification. Filesystem regressions cover private staging, no replacement and failed-copy cleanup. Required KVM proof must additionally show an ordinary foreign call, the configured machine/cgroup resources, a full memory snapshot, unchanged Postgres postmaster start time across fork restore, independent SQL mutations with `forked` grounding, finite-drive exhaustion without losing the existing marker, graceful stop and no owned runtime/copy leftovers. At the first bring-up the graceful stop is timed: the VMM must exit within a second of the acknowledged `STOP`, and the guest console log must show no kernel panic. The exit alone proves nothing, because `panic=1` makes a panic restart the guest and end the VMM exactly as a clean stop does; the absence of a panic trace is what separates them. No static test or absent-KVM branch counts as that proof.
