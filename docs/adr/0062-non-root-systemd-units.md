# 0062. Stable-user systemd units and source-aware credentials

- **Status:** Accepted (2026-11-13). Implemented; the installed fixture passed on 2026-11-14 (see Doctor and proof).
- **Date:** 2026-11-07
- **Amends:** ADR 0027 for the stable-user installation; the root service keeps its separate template, which is the unit of v0.4.1 byte for byte (a test pins its digest; v0.4.0's differs in one comment line), and ADR 0027's constraints.

## Decision

The nonroot daemon unit runs `kronik serve --rootless` (ADR 0060) and uses `User=kronik`, `Group=kronik`, `Delegate=yes`, no-new-privileges, strict filesystem protection, private tmp/devices/IPC, kernel/clock protections and the existing compatible seccomp denylist. Only `CAP_NET_BIND_SERVICE` is available for early listener binding. Startup explicitly clears every possessed host capability before logger/runtime threads, including Wasm-only degradation; entering the owned namespace subsequently grants only namespace-local authority.

`Wants=kronik-userns.service`, **not Requires**, orders the root setup unit without making Wasm availability depend on namespace creation. The setup unit exits after pinning. It does not unpin on ordinary stop/restart: matching pins must survive a live daemon/helper restart. Explicit unpin is ownership-token checked and reserved for stopped setup.

`ProtectControlGroups=private` is rendered only for systemd 257 or newer. The same source supports 255 using its discovered delegated cgroup path, without silently dropping actor limits. Data access uses explicit `ReadWritePaths`; recursive `StateDirectory` ownership repair is not used over mapped foreign data. Existing audit `LogsDirectory` support remains in both templates.

Do not add MemoryDenyWriteExecute, RestrictSUIDSGID, proc restrictions, private gateway networking, or an incompatible syscall allowlist merely to make the unit look stricter: Wasmtime, runsc, checkpoint restore and recorded network effects must still work. A required KVM device exception is explicit and installation removes its owned drop-in when disabled.

Which service `kronik serve --init` installs without a flag is one constant, `DEFAULT_MODE` in `crates/kronik/src/init.rs`. It is the root service until the nonroot one has been run on Ubuntu 24.04, the install target, and the maintainers have ruled. `--rootless` asks for the nonroot service and `--root` for the root one, whichever is the default. Making the nonroot service the default is a change of that constant, of the test that pins it and of the sentences in the guides that name the default.

## Credential rendering interface

The nonroot template uses `@KRONIK@`, `@CONFIG@`, `@KEY_CREDENTIAL@` and `@KEY_ARGUMENT@`; the root template uses only `@KRONIK@`, as v0.4.0's does, and carries no key path or credential (the root daemon reads the file named by `[keys] master_key_file` itself, so `--init --root` refuses a `--master-key-file` that differs from the configured one). Init renders the last two only for the nonroot unit and only for the selected **file** custody source:

- `LoadCredential=master-key:<selected source file>`;
- an ExecStart suffix ` --master-key-file %d/master-key`.

In the nonroot installation the key file stays outside the data directory, which the service user owns: systemd hands the file to the service as a credential, and a path inside a directory the service user controls is one it could redirect. `serve --init --rootless` refuses a file key under the data directory and says to keep it elsewhere (`/etc/kronik/master.key`, root-only, is the default) or to use `--root`. It refuses one under any other directory that anyone but root can change as well (every directory on the way must belong to root, with no write access for the group or others, and none may be a symbolic link; a sticky directory such as /tmp may be on the way, but not the one that holds the key or in which the installer creates the missing ones), because systemd reads the path as root.

The installer treats the data directory the same way. Everything it writes there (the `keys` directory and the KMS envelope of a first run) it writes while the directory is still root's and private (mode 0700), then hands the tree over to the service user by descriptor, files first and the data directory itself last, without following a link and only if it holds nothing but directories and regular files with one link. Once the directory belongs to the service user, a rerun reads nothing in it but the KMS envelope, through a descriptor with no symbolic link followed, and changes nothing in it: a process with the service user's uid can swap anything in that tree for a link, a FIFO or a socket. The databases are not opened by the installer; the service checks them when it starts. A directory left by a first run that stopped early (nothing but `keys`) is adopted.

`restore` run as root over the service user's tree does first what needs root, which is to read the master key, the credentials of an S3 remote and the keystore backup (of the bucket root handles only the wrapped key of a KMS source and the newest backup), then gives up root for good and finishes as the owner, inside the data directory (`.restore`): root reads nothing in the tree but the key file and the envelope of a KMS source, by name, and a `file://` remote is read by the owner afterwards. `upgrade check` and `foreign cleanup` also finish as the owner. `keys wrap` does not drop to the owner first: the KMS wrap needs provider credentials that only root may read, and `--remove-file` must delete a root-owned key file once the envelope is written. It, and the key and the envelope of a KMS source that lie in the data directory, reach files in a directory that belongs to another user only by name, through descriptors (`kronik_privacy::key_source`, on `owned_tree`): no link is followed, no FIFO, socket or file with a second link is opened, a file they create is given to the directory's owner before it appears, and a missing `keys` directory is an error and not a directory root makes. In a directory of their own user, such as a root installation's, paths work as they always did. The way to a directory of another user is opened again from `/` without following a symbolic link, and only through directories that root and the caller alone can change (the rule the installer applies to the data directory); a path through anything else, such as a directory under another user's home, is refused with the directory named. A file outside the data directory, such as the old key of `keys wrap --master-key-file`, is the operator's and is reached by path; that is decided by how the path is spelled, before anything is opened, and a failure to reach a file by name is a failure of the command, never a reason to try the path.

Environment/KMS sources get neither file credential directive nor file flag. Native `CREDENTIALS_DIRECTORY` provider paths and DynamicUser behavior are not replaced by a second provider stack or a TOML precedence override. Missing required source credentials fail closed. The daemon/shipper use the already loaded protected source; offline restore loads privileged source material before dropping authority, then writes as the validated destination owner under the same data lock.

## Doctor and proof

Doctor runs the nonroot checks (`userns`, `uid_view`, `subid`, `pin`, `delegate`) only with `--rootless`; without it `doctor` reports what it did before M21. Root `--rootless` changes to the actual stable service identity before namespace and sandbox smoke. If that identity cannot be established, it reports the limitation and cannot count a root-run smoke as success. The CAP_SETUID check keeps the detection of ADR 0027's trap, a root unit (or the doctor process) that lost `CAP_SETUID`, which is a failure. A nonroot unit is not examined: it holds no host capability by design, so the check looks at the doctor process instead, and with `--rootless` an ordinary-user doctor process checks its namespace-local authority and only warns. Being the service UID outside a delegated unit is not proof of effective installed-unit delegation/hardening. Separately, where a microVM tool bundle is installed and the root service runs, `microvm` checks that the daemon has the delegated cgroup leaf that a microVM needs and says how to add it (ADR 0061).

Tests assert the check sets with and without `--rootless`, what the CAP_SETUID check examines, and explicit rootless identity behavior. The installed fixture is designed to check the service identity and capabilities, the selected `LoadCredential` bytes and argument, read-only controls, usable delegated controllers, real writes and malicious-actor boundaries, and loaded-key shipping with the original source unavailable followed by an authenticated destination-owned restore. The installed fixture passed on 2026-11-14 on GitHub-hosted Ubuntu 24.04 runners (virtual machines on AMD hosts; Linux 7.0, systemd 255), through the manual `isolation` workflow, once with Ubuntu's AppArmor restriction on unprivileged user namespaces active (the image's default) and once with it lifted. It has not run on other distributions.

An existing installation of the other kind is not converted in place (ADR 0063): `kronik serve --init` refuses it and names the two ways forward, keeping it with `--init --root` or `--init --rootless`, or re-initializing and restoring the data with `kronik restore`.
