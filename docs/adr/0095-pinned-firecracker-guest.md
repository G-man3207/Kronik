# 0095. Pinned Firecracker guest and finite persistent drive

- **Status:** Proposed. Implemented, never run on a host with KVM; awaits maintainer ratification.
- **Date:** 2026-11-07

## Decision

M20 uses Firecracker 1.17.0, a source-built Amazon microVM Linux 6.18.25 kernel and the static musl `kronik-guest-init`. The daemon reads a digest-verified, protected tool manifest from `[foreign] microvm_dir`, default `/usr/local/lib/kronik/microvm`. It never downloads or builds tools. Missing usable KVM is `KVM_UNAVAILABLE`, with the suggestion to use gVisor; it is not a successful microVM test.

The explicit `scripts/build-microvm-tools.sh` recipe pins:

- Firecracker source commit `95f868c8e345b1cc8faccd1a3c910b4989dc3f58` and the upstream 1.17.0 release archive digest for the native architecture.
- Amazon Linux kernel commit `003a7905ac5f07e7f0e213951258d5bb80ea31e5`, whose Makefile version must be 6.18.25; the upstream Firecracker guest configuration's Git-blob identity is checked before `olddefconfig`.
- Source-built e2fsprogs 1.47.2 populates ext4 from the existing verified OCI directory, without libarchive or an intermediate image TAR. The small recorded `create_inode.c` patch (`scripts/e2fsprogs-1.47.2-directory-times.patch`) fixes host-construction atime/ctime while retaining original mtimes, including nanoseconds and post-2038 values, and root owner/mode/mtime/xattrs. Its archive, original/patched source and patch digests, original licenses, exact apply and regeneration commands are retained in `provenance.json` and `sources/`.

Measured output digests are generated by the build, never guessed in source. Both real two-location root-image proofs (installed filesystem tools before kernel compilation, then the complete manifest before publication) are mandatory, each requiring exactly one passed test and no failures or ignored tests. A failed build retains its sources/logs outside the final tool installation. Tool manifests contain public build identities, not secrets: protected read-only publication can be root-owned and readable by the service user; write permission is never delegated merely to make the manifest readable.

The actual native-musl guest build and static-ELF check also precede the long kernel compile. `--kernel-from /owned/completed-build` reuses only a protected kernel whose `sources/kernel-provenance.json` matches the pinned source/configuration, architecture, build epoch, resolved tool hashes, header-library versions and recorded build environment. Every fixed kernel/source/config/recipe/log artifact is rehashed before reuse; mismatches fail instead of silently rebuilding or substituting a different kernel. The original producer recipe, source archive, logs and receipt remain in the new bundle. A recovered receipt explicitly identifies a completed kernel observed before a later guest-build failure; it is not represented as an earlier automatically emitted receipt or a hardware boot result.

The separate host filesystem tools use the supported OS's replaceable shared libraries; only guest-init is static musl. Actual resolved library names/paths/hashes, installed package identities, tested host OS and original package copyright files with referenced full license texts are retained in `provenance.json`, `sources/host-licenses/` and `HOST_TOOLS_THIRD_PARTY_LICENSES.txt`. These host library binaries/runtime packages are not bundled. Their recorded hashes describe the build/proof host, not a runtime lockout of interface-compatible modified libraries or a portable glibc-baseline claim. Missing attribution fails before the long kernel build.

OCI digest verification, whiteouts, bounded extraction, image user, arguments, environment, working directory and capability intent remain shared with the existing backends. OCI archive timestamps, hard links, xattrs and implicit-directory metadata reach the directory formatter without a blanket `SOURCE_DATE_EPOCH` mtime clamp. No shell, init binary or configuration file is written into the image tree. A private initramfs supplies `/init`, a bounded `/config.json` and the initial console node without host `mknod`.

The guest mounts the image's ext4 root read-only, places its writable overlay in guest tmpfs, and mounts a separate writable **1 GiB block device** at `/data`. This is block-device capacity, not 1 GiB of application-usable space after ext4 metadata. The full host data-file allocation is reserved before publication. Native `-E nodiscard` disables initial discard, and `UNIX_IO_NOZEROOUT=1` uses explicit zero writes instead of libext2fs's unsupported-ZERO_RANGE-to-hole-punch fallback; the full allocation check is not weakened. Existing data is never silently resized, replaced or reformatted; sparse or malformed existing drives are refused without changing them. Normal guest boot changes only the mounted `/data` root's ownership to the resolved image UID/GID, as the existing OCI backend does. Contents are not recursively reowned.

The fixed data-drive capacity is not a new cross-backend quota API. Existing gVisor/trusted host-directory `/data` binds remain without an automatic hard quota. Operators needing that boundary must preprovision a separate/quota-enabled filesystem. Disk-reserve admission is not a write-time hard quota. The authoritative brief does not request a generic persistent per-actor disk-quota ABI; no host quota activation or mandatory generic data migration is added here.

## Host boundary and resource accounting

Only a single-threaded internal child launcher enters the VMM jail. It uses the existing `Env::procs` runner, not a second process framework. Fixed mounts expose the verified runtime/kernel/initrd, read-only root disk, writable data disk/output and the existing `/dev/kvm`. It creates private mount/network/IPC/UTS/cgroup namespaces, pivots away from the old root, drops capabilities, enables no-new-privileges and arms parent-death termination. There is no guest NIC, network-forwarding service, arbitrary bind list, command template or unjailed fallback.

This launcher replaces Firecracker's jailer, which needs root; upstream recommends the jailer for production, and the replacement is Kronik's own security-critical code (`sys::jail_microvm`), not reviewed upstream. One thing upstream recommends is not done: the launcher does **not switch to a distinct uid** per VMM. The VMM runs as the daemon's own identity (namespace root in the rootless installation) with every capability cleared, the bounding set emptied, the secure bits `NOROOT` and `NOROOT_LOCKED` set (so that an exec as uid 0 gains nothing even without no-new-privileges: on a root installation the VMM is uid 0) and no-new-privileges set. It does have a **PID namespace of its own**, because without one a VMM compromised by a guest escape could abort any process of the same uid by thread id: Firecracker's default seccomp filter (v1.17.0) allows `tkill` for two signals (SIGABRT, SIGRTMIN) and looks at no thread id, and on a root installation "the daemon's uid" is every root process of the host, PID 1 included, whose SIGABRT handler in systemd 255 freezes the manager until a hard reset. The launcher unshares `CLONE_NEWPID` with its other namespaces and forks; the child is init of the new namespace and execs the VMM, so `kill(1, ...)` is the VMM itself and every host thread id is `ESRCH`; the parent stays in the VM's cgroup, resident (a few MiB) next to the VMM, so the cgroup's memory limit covers both and the calibration of that limit records the cgroup's peak with both processes; it gives up every capability, waits, and exits with the child's status (128 plus the signal when a signal ended it). The child arms the parent-death signal itself (fork clears it) and checks a pipe that only the parent holds, because `getppid()` is 0 for the init of a namespace whose parent is outside; killing a namespace's init kills the namespace, so the daemon's death or kill of the launcher ends the VMM. Every descriptor above 2 is closed at the start of the launcher and again before `pivot_root`. The rehearsal tests run this sequence in throwaway user, mount and PID namespaces (never with KVM): the VMM is pid 1, host processes and threads are `ESRCH`, a program executed in the jail finds no capability, an empty bounding set, the secure bits set and no ambient capability, the status and signal relays, and the VMM's death with its launcher. Unverified on real KVM: Firecracker as pid 1. Firecracker is started as `/firecracker --api-sock /api.sock` with an empty environment; no seccomp option is passed, so its built-in filters apply (to be confirmed on a KVM host). Upstream's side-channel guidance for multi-tenant hosts (SMT, KSM, swap) is the operator's host setup and is not managed here.

A microVM requires an owned delegated cgroup with an empty parent and a daemon leaf. Arbitrary root shells do not infer ownership from root's ability to write cgroup files. The root unit is v0.4.0's and delegates nothing, so a root installation adds the leaf with the drop-in of the operations guide (ADR 0061), and a microVM add without it is refused; rootless startup discovers the actual delegated subtree, including the `/` representation in a private cgroup namespace. Actor VMM instances have unique private runtime/cgroup identities, so delayed checkpoint/stop work cannot address a removed-and-readded actor's new VM.

CPU declarations remain exact milliCPU cgroup quotas over 100 ms. Firecracker topology is rounded up to one vCPU or an even number, at most 32; requests above 32 CPUs are rejected. Guest RAM is at least 128 MiB, rounded down to whole MiB and checked for the API's representable range. The VMM cgroup memory limit is guest RAM plus a fixed 128 MiB host overhead allowance, with swap disabled and a 1,024-pid limit. This overhead is not guest RAM and is not an operator-controlled unrecorded quota. Required real-KVM conformance must record machine configuration and cgroup peak/current memory under the documented workload; the constant is not described as calibrated until that result exists.

## Proof and limits

Required proof is actual boot, ordinary `foreign.http` over vsock, malicious-actor controls, finite-drive ENOSPC without losing existing data, full snapshot and sandbox-fork restore, independent fork writes, graceful stop and filtered cleanup. Parser, filesystem and lifecycle regressions supplement that proof; they cannot manufacture a KVM pass, and a run on a host without `/dev/kvm` is not one. None of this has been run: no real Firecracker instance has booted under this code, and the pinned tool bundle has not been built on this revision. Where the proof runs (a hosted runner with `/dev/kvm`, a self-hosted runner, or a documented script on a KVM host) is a separate decision.

Images whose user or file owners lie outside the user namespace's mapped range cannot be unpacked in the rootless installation: unpacking changes ownership inside the namespace and there is no admission check for the range, so the failure shows when the actor starts, not at `foreign add`. The failed ownership change reports "owner U:G is outside the ids this installation maps" and what to do, instead of a bare errno.
